# 第 22 课 · 属性增强：[[nodiscard]]、[[maybe_unused]]、[[fallthrough]]（C++17）

> 所需标准：**C++17** ｜ 讲解：本文件 ｜ 独立代码：`22_attributes.cpp`

## 一、底层原理

### 1.1 属性是什么：写给编译器的"意图标注"

属性（attribute）**不改变程序语义**，只影响诊断与优化提示。
C++11 只有 `[[noreturn]]` 等；第 09 课讲了 C++14 的 `[[deprecated]]`；
C++17 一次补齐三个高频属性——全部在治同一个病：

**代码没错，但编译器分不清"程序员忘了"还是"程序员故意的"。**

| 属性 | 意图声明 | 治的病 | 警告位置 |
|---|---|---|---|
| `[[nodiscard]]` | 返回值必须消费 | 忘接返回值（find 忘看、async 忘 wait） | **调用点** |
| `[[maybe_unused]]` | 这个名字可能未用 | 条件编译下参数/变量"半身不遂" | 声明点（压制） |
| `[[fallthrough]]` | 贯穿是故意的 | switch 有意省 break 被误报 | case 内（声明） |

属性把意图写进代码，警告从"噪音"变成"信号"——这是零成本的最廉价防御。

### 1.2 nodiscard 的传染性（最有用的细节）

`[[nodiscard]]` 能标函数，还能标**枚举与类**。标在类上：**所有返回该类的
函数自动获得"丢弃即警告"**。标准库连夜给 `std::error_code` 标了它——
所以第 21 课 `fs::file_size(p, ec)` 忘接 `ec` 会警告。C++23 的
`std::expected`（第 50 课）同样是 nodiscard 家族：错误处理链的每一环
都由编译器盯着。

### 1.3 maybe_unused 与 fallthrough 的机制

- `[[maybe_unused]]`：压制"未使用"警告（变量/形参/字段/……）。
  与 C 风格 `(void)x;` 假消费相比：不产生代码、意图明确、作用域精确
- `[[fallthrough]];`：只允许出现在 case 内、**下一个 case 标签之前**，
  本质是一条"空语句 + 属性"——告诉 `-Wimplicit-fallthrough` 这是设计

## 二、具体语法

```cpp
[[nodiscard]] int compute();               // 函数
enum class [[nodiscard]] Status { Ok };    // 枚举：返回 Status 的都受保护
struct [[nodiscard]] Result { bool ok; };  // 类：同上（推荐 —— 一次标注，
                                           //      全部返回点受益）
[[maybe_unused]] int x = setup();          // 变量
void f([[maybe_unused]] int line);         // 形参
switch (c) {
    case 'a':
        [[fallthrough]];                   // 分号必须有 —— 这是一条语句
    case 'A':
        return 1;
}
```

规则细则：

- `[[fallthrough]];` 是**语句**（属性 + 空语句），分号不可少；
  放在最后一个 case 里无意义且报错
- `[[nodiscard]]` 对 `void` 返回无意义
- C++20 起支持 `[[nodiscard("理由字符串")]`（第 41 课预告）
- 属性写在**声明**处（头文件），不是定义处

## 三、实际应用与最佳实践

### 3.1 场景：错误处理链全链路防丢（示例 ③）

`ParseResult`（nodiscard 类）从 `parse_int` 返回——任何调用点敢丢弃，
编译器当场警告。这是错误码风格起死回生的关键：**没有它，错误码会被
无声吞掉**；有了它，错误码 + nodiscard ≈ 轻量版 expected。

### 3.2 场景：多配置代码与状态压缩

- 日志函数在 Release 构建里不用 `line` 形参 → `[[maybe_unused]]`
- switch 把 `'a'`/`'A'` 压到同一档（贯穿即语义）→ `[[fallthrough]]`

### 3.3 最佳实践清单

1. "忽略返回值 = bug"的函数一律 nodiscard：工厂、find、分配、变换、重试
2. 错误/结果类型直接定义成 nodiscard 类——一次标注，全部返回点受益
3. `[[maybe_unused]]` 只在警告真实出现时加，不做预防性涂抹
4. 有意贯穿必写 `[[fallthrough]]`，让 `-Wextra` 常开无噪音
5. 属性放头文件声明处；代码评审时把属性当接口契约读

## 常见陷阱

1. `[[fallthrough]]` 与 `break` 写反位置：属性必须**贴着下一个 case 之前**，
   放在 case 标签之后、表达式之前才对；写成 `case 'a': [[fallthrough]]; case 'A':`
2. 试图用 `(void)f()` 压制 nodiscard——实现定义行为（有的编译器照样警告），
   别依赖
3. `[[maybe_unused]]` 涂太广：拼错变量名从此不警告——压制范围越小越好
4. 标在定义而非声明上：换 TU 调用就看不到属性
5. 以为属性是运行期检查——它只在编译期发诊断，语义零影响

## 练习

1. 给第 16 课 `find_age` 的返回包一层 nodiscard 类 `Found{bool ok; int age;}`
   （或直接标函数），故意丢弃调用一次，记录警告文本。
2. 写 `debug_log([[maybe_unused]] const char* tag)`：Debug 构建打印 tag、
   Release 不打印（用 `#ifdef` 切换），验证两种构建都零警告。
3. 用 `[[fallthrough]]` 写 token 压缩器：`' ','\t','\n'` 全部贯穿到"空白"档。
4. 把 `try_once` 的返回从枚举换成 `Status2 { Ok, Retry, Fail }` 结构体
   （不加属性），对比枚举版与结构体版丢弃调用的警告差异。
