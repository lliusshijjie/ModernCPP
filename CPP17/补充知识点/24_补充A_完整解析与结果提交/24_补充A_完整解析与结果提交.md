# 补充 24A · 完整解析与结果提交（C++17）

> 阅读顺序为第 24 课之后，不占每日主线编号。
> 所需标准为 C++17。配套代码见 [24a_strict_charconv.cpp](24a_strict_charconv.cpp)。

## 一、底层原理

### 1.1 转换成功与输入完全有效，需要分别判断

`from_chars` 回答的是“从开头能读出什么数值”。
对 `"8080ms"`，它可以成功得到 8080，ec 为零，ptr 指向 m。
这符合前缀解析的约定，但不符合“整个字段必须是一个端口号”的业务要求。

严格解析可以分成三层：

| 层次 | 检查 | 失败示例 |
|---|---|---|
| 数值转换 | ec 是否表示成功 | 空白开头、非法字符、目标数值类型溢出 |
| 完整消费 | ptr 是否等于 last | `8080ms`、`80 ` |
| 业务范围 | 数值是否符合接口约定 | 本例拒绝 0、负数和大于 65535 的值 |

本例选择端口范围 1～65535，是这个练习接口的约定。
其他接口可能允许端口 0，不能把这里的范围当作所有网络接口的统一规则。

### 1.2 需要失败不改结果时，先用局部候选值

```cpp
long long candidate = 0;
auto [ptr, ec] = std::from_chars(first, last, candidate);
// 检查转换结果、消费位置、业务范围……
output = static_cast<unsigned>(candidate); // 所有检查通过之后才提交。
```

from_chars 在 invalid_argument 或 result_out_of_range 时不改目标值。
但 `"8080ms"` 属于转换成功，传入的目标值已经被改成 8080。
如果之后才发现尾部多余字符，调用者的状态就可能被部分更新。

局部 candidate 将“转换过程”与“更新业务状态”分开。
任何检查失败时，调用者原来的 output 都保持不变。

## 二、具体语法

### 2.1 不要丢掉错误类别与消费位置

示例返回一个带 nodiscard 的小结构：

```cpp
struct [[nodiscard]] ParseReport {
    ParseError error;
    std::size_t consumed;
};
```

枚举分别表示空输入、非法起始、数值类型溢出、多余尾部与业务范围错误。
consumed 表示 from_chars 匹配的字符数：
`"8080ms"` 为 4，纯数字溢出串也可能全部匹配，不能据此认定转换成功。
调用方必须先看 error，再按需要报告位置。

本例先处理空视图，之后才计算 data() + size() 和指针差。
这使默认构造的空 string_view 也有明确分支，不需要对可能为空的指针做运算。

### 2.2 明确接受的字符语法

本例固定使用十进制整数转换：

- 不跳过空白，`" 80"` 失败。
- 不接受前导加号，`"+80"` 失败。
- candidate 为有符号整数，`"-1"` 数值转换成功，再被业务范围拒绝。
- 整数 base 必须在 2～36 之间，不能传 0 来要求自动识别进制。
- 要接受尾部单位、空格或进制前缀，应在接口中明确约定并自行处理。

这里的 consumed 是匹配进度，不是所有失败原因都对应一个“出错字符”。
例如超出业务范围时，整个数字已经匹配，范围错误属于下一层校验。

### 2.3 to_chars 失败不能当作截断成功

to_chars 缓冲不足时报告 value_too_large，ptr 等于 last，
缓冲区内容未指定。不能把这部分内容当作较短的合法结果使用。

成功时用 `[first, ptr)` 表示实际输出：

```cpp
auto result = std::to_chars(buffer.data(), buffer.data() + buffer.size(), 8080);
// 检查 result.ec 后：
std::string_view encoded{buffer.data(),
    static_cast<std::size_t>(result.ptr - buffer.data())};
```

to_chars 不自动附加零字符。按长度使用结果就不需要补零；
交给仅接收 C 字符串的接口时，还需预留位置并自行补终止符。

## 三、实际应用与最佳实践

示例把 output 预设为 443，然后分别尝试正常值、尾部单位、前导空白、
加号、负数、上下边界和溢出串。除三个合法输入之外，output 始终保持 443。

这个结构适合配置字段、命令行数值参数和文本协议：
底层转换只负责读数字，接口再决定完整字段的语法与范围，
最后才更新原来的配置。构造提示文字或保存字符串仍可能分配内存；
不应由转换函数本身的特性推断整个业务过程没有分配。

## 常见陷阱

- 只检查 ec，接受了数字后面的垃圾字符。
- 直接写入 output，再在完整消费或业务范围检查时失败，留下已修改的状态。
- 把 from_chars 的溢出理解为目标变量变成未定义值；它保证目标值不变。
- 把 to_chars 失败后的内容当成截断输出；它没有这种约定。
- 对浮点格式统一套用“最短往返”结论；带精度的输出可能主动舍入，
  需要按对应重载的格式约定理解。

## 完整示例

从仓库根目录执行：

```powershell
g++ -std=c++17 -Wall -Wextra -Wpedantic "CPP17/补充知识点/24_补充A_完整解析与结果提交/24a_strict_charconv.cpp" -o run.exe
.\run.exe
```

第一段输出 `prefix: 8080 true false`。
十一组输入分别检查错误类别与 output 是否符合预期，其中空输入使用默认构造的空视图。
最后输出 `small buffer rejected: true`、
`encoded: 8080 length=4` 和 `checks: PASS`。

## 练习

1. 保持失败不修改 output 的约定，让接口接受两端空格，说明 consumed 如何定义。
2. 增加 `"65535x"`，分别判断转换、完整消费与业务范围各层的结果。
3. 设计一个允许单位 ms 的解析器，明确是否接受空格、大小写和空单位。
