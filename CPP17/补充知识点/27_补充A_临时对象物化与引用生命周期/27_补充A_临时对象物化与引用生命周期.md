# 补充 27A · 临时对象物化与引用生命周期（C++17）

> 阅读顺序为第 27 课之后，不占每日主线编号。
> 所需标准为 C++17。配套代码见 [27a_temporary_lifetimes.cpp](27a_temporary_lifetimes.cpp)。

## 一、底层原理

### 1.1 强制拷贝消除，不代表临时对象从此不存在

`Ticket value = make_ticket(7);` 中，同类型 prvalue 可以直接初始化 value。
当改为 `const Ticket& ref = make_ticket(7);` 时，引用需要绑定到一个实际对象，
于是发生临时对象物化：产生临时 Ticket，并用相应的 glvalue 表达式指代它。

本例的 Ticket 删除拷贝和移动构造，仍可从工厂按值返回。
它还记录活着的 Ticket 数量，用来观察实际对象何时析构。
只是不需要拷贝/移动构造，并不意味着析构函数也可以不可访问或被删除。

### 1.2 寿命取决于如何绑定，不取决于有没有写 const auto&

几种写法需要分别判断：

| 形式 | 本例中的生命周期 |
|---|---|
| `const Ticket& a = make_ticket(7);` | 临时对象寿命延长到 a 的作用域结束 |
| `Ticket&& b = make_ticket(8);` | 此局部右值引用也延长临时对象寿命 |
| `read_id(make_ticket(9));` | 临时实参活到包含调用的完整表达式结束 |
| `const int& n = make_ticket(10).id;` | 直接通过成员访问绑定子对象，延长整个 Ticket 的寿命 |

最后一种情况下，id 不能脱离包含它的 Ticket 独立生存；
语言规则会将对应临时拥有者一并保留。
它与“先调用一个返回内部引用的函数，再绑定引用”的规则不同。

## 二、具体语法

### 2.1 具名右值引用表达式是 lvalue

```cpp
Ticket&& named = make_ticket(8);
static_assert(std::is_same_v<decltype(named), Ticket&&>);
static_assert(std::is_same_v<decltype((named)), Ticket&>);
```

decltype(named) 的特殊规则取得这个名字声明的类型。
decltype((named)) 按表达式值类别判断：表达式 named 是 lvalue，
因此得到 Ticket&。声明中的 && 与使用这个名字时的表达式类别，不是一回事。

配套示例提供 const Ticket& 和 Ticket&& 两个重载。
传 named 选择左值版本；传 std::move(named) 选择右值版本。
后者只绑定引用，完全没有调用 Ticket 的移动构造，所以删除移动构造也能通过。

### 2.2 函数返回引用不会把临时实参的寿命传递出去

```cpp
const Ticket& relay(const Ticket& value) { return value; }
// 仅用于分析：下面的 ref 在分号之后悬空，不能读取它。
// const Ticket& ref = relay(make_ticket(7));
```

临时 Ticket 作为实参活到整个调用所在的完整表达式结束。
把 relay 返回的引用再绑到另一个引用，不会重新延长原临时对象的寿命。
同理，std::move 是函数模板调用，`std::move(make_ticket(7))`
不会仅因为外面又绑定一个局部引用，就获得新的寿命延长。

不要运行悬空读取来“验证看上去仍然正常”。
本例通过活对象计数展示正常销毁点，危险写法只用于说明。

### 2.3 用引用限定符约束借用接口

CachedTicket 拥有一个 Ticket，并提供一个借用接口：

```cpp
const Ticket& view() const & { return value_; }
const Ticket& view() const && = delete;
```

const & 与 const && 是成员函数的引用限定符，约束隐式对象参数。
它们是 C++11 已有语法，这里用来保护 C++17 按值创建的对象。

对于有名字、仍由调用方持有的 owner，可以调用 owner.view()。
对于 CachedTicket{99}.view()，重载决议选到已删除的右值版本，
从而在编译期拒绝从临时拥有者借出引用。

这个约束只能减少一种误用。
调用者若将借用引用保存到 owner 析构之后，依然会悬空；
是否使内部对象失效、是否存在并发修改，也需要接口另行约定。

## 三、实际应用与最佳实践

这种区分适合容器视图、解析结果的字段访问，以及返回内部缓存引用的接口。
先确定谁拥有对象，再判断借用是否越过拥有者的生命周期。

只需要一个小结果时，可以像 read_id 一样直接返回 int 值，
使调用方不必继续维护借用关系。
需要返回非拥有视图时，则明确约定拥有者，并考虑是否限制临时对象上的调用。
第 20 课的 string_view 同样不会替使用者延长底层字符的寿命。

## 常见陷阱

- 把“没有拷贝”理解成“没有对象、不需要析构”。
- 看到 Ticket&& 就认定使用 named 表达式一定选择右值重载。
- 把 std::move 当成移动构造；本例 Ticket 不可移动，仍可将引用转换为 xvalue。
- 用函数返回引用间接绑定临时对象，却套用直接绑定时的寿命延长规则。
- 认为删除临时对象上的 view 调用，就解决了所有引用悬空问题。

## 完整示例

从仓库根目录执行：

```powershell
g++ -std=c++17 -Wall -Wextra -Wpedantic "CPP17/补充知识点/27_补充A_临时对象物化与引用生命周期/27a_temporary_lifetimes.cpp" -o run.exe
.\run.exe
g++ -std=c++17 -Wall -Wextra -Wpedantic -fno-elide-constructors "CPP17/补充知识点/27_补充A_临时对象物化与引用生命周期/27a_temporary_lifetimes.cpp" -o no_elide.exe
.\no_elide.exe
```

两版预期输出一致，包含 `named expression: lvalue`、
`move expression: rvalue`、`parameter read: 9 alive=0`、
`member owner alive: 1` 和 `checks: PASS`。
关闭可选消除不会破坏这里的强制构造与寿命规则。

单独开启误用诊断，预期编译失败：

```powershell
g++ -std=c++17 -DLESSON27A_TEMP_VIEW -Wall -Wextra -Wpedantic "CPP17/补充知识点/27_补充A_临时对象物化与引用生命周期/27a_temporary_lifetimes.cpp" -o bad_view.exe
```

诊断应指向已删除的 const && 版本 view；默认代码不会读取悬空引用。
