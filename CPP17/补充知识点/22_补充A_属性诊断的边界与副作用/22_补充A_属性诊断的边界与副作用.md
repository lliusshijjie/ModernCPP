# 补充 22A · 属性诊断的边界与副作用（C++17）

> 阅读顺序为第 22 课之后，不占每日主线编号。
> 所需标准为 C++17。配套代码见 [22a_attribute_diagnostics.cpp](22a_attribute_diagnostics.cpp)。

## 一、底层原理

### 1.1 nodiscard 提醒检查，调用方仍要处理结果

C++17 的 `[[nodiscard]]` 鼓励编译器对无意丢弃结果发出警告。
它不会替调用者判断成功、失败或重试，也不保证所有编译器配置都拒绝该程序。
开启适当警告，再把相关警告视为错误，才能在构建时实施项目约束。

下面两种写法关注的范围不同：

```cpp
[[nodiscard]] int compute();       // 标在函数：提醒调用者检查这个函数的返回值。
struct [[nodiscard]] Validation { bool ok; }; // 标在类型：覆盖按值返回该类型的调用。
Validation validate(int, int&);
Validation& last_result();        // 引用返回，不自动继承类型上的诊断。
```

指针返回也不会因为所指类型带属性而自动获得这种提醒。
如果返回引用或指针的某个函数也不应被忽略，可以直接标记该函数。

### 1.2 显式丢弃是允许表达的意图

```cpp
(void)validate(-1, calls);
```

显式转换到 void 是标准对这种丢弃场景列出的例外。
该函数仍会调用，副作用仍会发生；只是返回值被有意忽略。
`[[maybe_unused]] auto result = validate(...);` 也可能压住未使用变量警告，
但仍不代表 result 内的业务状态已经得到检查。

另外，C++17 没有要求 `std::error_code` 类型带 nodiscard。
`fs::file_size(path, ec)` 把错误写入引用参数 ec，
是否随后读取 ec，不属于该属性能跟踪的范围。

## 二、具体语法

### 2.1 maybe_unused 不会阻止初始化或实参求值

示例中的日志函数只在未定义 NDEBUG 时打印参数：

```cpp
void debug_trace([[maybe_unused]] int value) {
#ifndef NDEBUG
    std::cout << value;
#endif
}
```

调用 `debug_trace(++evaluated)` 时，两种构建中的 evaluated 都会增加。
属性没有删除形参，也没有改变函数调用的求值规则。
同样，`[[maybe_unused]] auto x = side_effect();` 仍执行初始化表达式。
如果 Release 确实需要完全省略日志参数的计算，应在调用处设计条件编译或其他控制机制。

### 2.2 fallthrough 声明下一步贯穿的意图

```cpp
switch (detail) {
case Detail::Full:
    show_advanced();
    [[fallthrough]];
case Detail::Basic:
    show_basic();
    break;
}
```

`[[fallthrough]];` 标记一条空语句，不等同于 break，也不会跳过下一分支的代码。
随后执行的语句必须是同一个 switch 的 case 或 default 标签语句。
把它放到最后一个分支后、且没有后续标签，是不合法的。

多个空 case 共用一段处理逻辑，通常直接并列标签即可。
当上一个分支确实执行了工作，再有意进入下一个分支时，这个标注最能帮助阅读。

## 三、实际应用与最佳实践

示例把三个属性放在各自有用的位置：

| 位置 | 用途 | 调用者仍负责什么 |
|---|---|---|
| 校验结果类型 | 提醒接收按值返回的结果 | 实际读取并处理 ok |
| 调试日志形参 | 兼容 Debug / Release 的使用差异 | 决定是否求值日志实参 |
| 分档帮助菜单 | 说明 Full 还会打印 Basic 内容 | 保证贯穿符合业务顺序 |

要把属性当成接口提示来评审：结果为什么不能随意丢弃，参数为什么可能未用，
贯穿为什么合理。它们不能替代错误处理、状态检查或控制流设计。

## 常见陷阱

- 把类属性理解为覆盖所有引用、指针返回；必要时直接标函数。
- 认为用了 nodiscard 就不会吞错；保存结果却从不读取状态，仍可能漏错。
- 把 maybe_unused 当成“去掉这段计算”；初始化和调用实参依然执行。
- 以为所有属性都只影响警告；本节讨论这三个属性，其他属性有各自规则。
- 在 C++17 使用 `[[nodiscard("原因")]]`；理由字符串属于 C++20 的扩展。

## 完整示例

在仓库根目录分别构建默认版与 Release 版：

```powershell
g++ -std=c++17 -Wall -Wextra -Wpedantic -Werror "CPP17/补充知识点/22_补充A_属性诊断的边界与副作用/22a_attribute_diagnostics.cpp" -o run.exe
.\run.exe
g++ -std=c++17 -DNDEBUG -Wall -Wextra -Wpedantic -Werror "CPP17/补充知识点/22_补充A_属性诊断的边界与副作用/22a_attribute_diagnostics.cpp" -o run.exe
.\run.exe
```

两版都输出 `calls: 2`、`argument evaluations: 1` 和 `checks: PASS`。
Release 版少一行 `debug value: 1`，帮助菜单仍按 advanced、basic 的顺序打印。

可单独开启一个故意丢弃结果的调用，观察 GCC 诊断：

```powershell
g++ -std=c++17 -DLESSON22A_DISCARD -Wall -Wextra -Werror=unused-result "CPP17/补充知识点/22_补充A_属性诊断的边界与副作用/22a_attribute_diagnostics.cpp" -o discard.exe
```

这条命令预期编译失败，诊断包含丢弃 Validation 返回值的 unused-result。
诊断措辞由编译器决定。默认构建未开启该实验分支，可以正常通过严格编译。

## 练习

1. 给 last_result 函数本身添加 nodiscard，再丢弃调用结果，比较诊断。
2. 把 debug_trace 的调用也放到条件编译中，比较 Release 下 evaluated 的值。
3. 在帮助菜单增加 Summary 档，先画出预期打印顺序，再决定贯穿位置。
