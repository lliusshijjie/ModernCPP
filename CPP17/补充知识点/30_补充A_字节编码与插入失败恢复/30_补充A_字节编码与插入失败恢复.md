# 补充 30A · 字节编码与插入失败恢复（C++17）

> 阅读顺序为第 30 课之后，不占每日主线编号。
> 所需标准为 C++17。配套代码见 [30a_byte_cache_recovery.cpp](30a_byte_cache_recovery.cpp)。

## 一、底层原理

### 1.1 字节类型不会自动决定协议表示

std::byte 区分原始字节与算术数值，但没有替协议选择字段宽度、字节序或编码格式。
把一个结构体的内存直接当成协议内容，还可能包含填充、平台字节序等差异。

本例只编码一个 16 位无符号值，约定高 8 位在前、低 8 位在后。
0x1234 对应两个元素 0x12、0x34，解码时显式移位和合并。
这种写法不依赖整数本机内存的高低字节排列。

示例使用 std::array<std::byte, 2> 与 std::to_integer<unsigned>，
并在编译期检查往返结果。
同一 std::byte 类型之间可以比较；不能由“不支持算术”推出“比较也全部禁止”。

### 1.2 try_emplace 延迟元素构造，不延迟实参求值

```cpp
cache.try_emplace("alpha", make_code());
```

即使 alpha 已存在，调用 make_code() 的步骤也发生在进入 try_emplace 之前。
库可以在查到重复键后不构造 Frame，但已经发生的工厂调用不会被撤销。

这与下面的写法并不冲突：

```cpp
cache.try_emplace("alpha", std::move(pointer));
```

std::move 本身只是转换值类别。
重复键分支不使用该实参去构造元素，因此不会因为这次转发而搬走 pointer。
“没有移动构造”和“实参表达式没有执行”必须分别理解。

## 二、具体语法

### 2.1 避免昂贵工厂，需要显式安排调用时机

在这个单线程示例里，可以先查找，再在缺失分支调用工厂：

```cpp
if (cache.find("alpha") == cache.end()) {
    cache.try_emplace("alpha", make_code());
}
```

这可能增加一次查找，却能避免重复键时执行昂贵计算。
也可以让 mapped type 的构造函数接收便宜的构造参数，
让真正的资源构造由 try_emplace 在插入分支完成。

查找再插入不是跨线程的原子流程。
共享容器仍要遵守统一的同步协议，不能仅靠这个分支处理并发。

### 2.2 next_id++ 仍然会执行

```cpp
unsigned next_id = 1;
ids.try_emplace("known", next_id++);
ids.try_emplace("known", next_id++);
```

执行后 next_id 为 3，表中的首次编号仍为 1。
如果编号只允许在真正插入时增长，应改为：

```cpp
auto [position, inserted] = ids.try_emplace(word, next_id);
if (inserted) ++next_id;
```

这个模式可以用于词典编号、首次出现序号和无跳号的本地登记过程。
还需按业务规模考虑编号上限与并发同步。

### 2.3 不带 hint 的节点插入失败，接住返回的 node

示例从 cache 提取 alpha，将其 key 改成已存在的 taken，再尝试插回：

```cpp
auto result = cache.insert(std::move(node));
if (!result.inserted) {
    result.node.key() = "restored";
    auto restored = cache.insert(std::move(result.node));
    // 继续检查 restored.inserted。
}
```

键冲突时，原 taken 不会被覆盖；待插入节点由 result.node 持有。
如果直接丢弃这次 insert 的返回值，返回对象析构时会销毁它持有的节点。
这属于 RAII 释放，不等于业务数据已经得到恢复。

带 hint 的 insert 重载有不同的失败保留约定，
不能只看函数名就套用同一种所有权流转。

### 2.4 把节点身份、指针有效性与分配器前提分开

Frame 删除拷贝和移动构造，try_emplace 仍可就地构造它，
节点提取和再插入也不需要移动其中的 Frame。

示例在 extract 前保存 Frame*，在节点重新进入容器之后才再次使用。
extract 会使对应迭代器失效；原指针和引用不因此失效，
但元素由节点句柄持有期间，不能通过这些原指针和引用访问元素。
若从 node.mapped() 取得引用或指针，它们还有成功再插入后失效的相应约定，
不能与 extract 前保存的指针混为一谈。

跨容器插入非空节点时，还要满足节点兼容性与分配器相等的前提。
本例在同一个、使用默认分配器的 map 中操作，避免引入自定义分配器代码。
节点搬移不重建 Frame，也不意味着改 key、比较键或整个业务过程从不分配、不抛异常。

## 三、实际应用与最佳实践

本例把一个字节帧作为缓存值，先演示数值与字节表示的明确转换，
再用构造计数区分实参求值与元素构造，最后在键冲突后恢复原节点。

检查结果包括：

- 工厂调用了一次，但重复键没有增加 Frame 构造数。
- next_id 在两次调用后增长为 3。
- taken 原值保持 0xCAFE，恢复后的 Frame 仍表示 0x1234。
- 从头到尾只构造两个 Frame，恢复后对象地址仍相同。

这适合需要改名、迁移或保存不可移动资源值的关联容器。
恢复逻辑要明确处理“节点现在由谁持有”，而不是只看插入有没有成功。
本例验证正常的冲突恢复，没有声称对键赋值、分配器或比较器抛出的任意异常都实现回滚。

## 常见陷阱

- 把 std::byte 当成已经定义好的跨平台协议格式。
- 认为 try_emplace 重复键时会跳过工厂调用或 next_id++。
- 认为 emplace 重复键必然搬空实参；标准允许构造后再丢弃，但不要求所有实现都消耗它。
- 忽略 insert(node) 的返回对象，导致冲突节点随临时返回对象被销毁。
- 在节点仍被句柄持有时，通过 extract 前取得的指针访问元素。
- 跨容器搬节点时只检查 key/value 类型，却漏掉分配器等前提。

## 完整示例

从仓库根目录执行：

```powershell
g++ -std=c++17 -Wall -Wextra -Wpedantic "CPP17/补充知识点/30_补充A_字节编码与插入失败恢复/30a_byte_cache_recovery.cpp" -o run.exe
.\run.exe
```

预期输出 `wire: 18 52 value=4660`、`factory/constructions: 1 1`、
`next id: 3`、`collision kept node: true`、
`same frame: true constructions=2`，最后为 `checks: PASS`。

## 练习

1. 将编码格式改成低 8 位在前，更新期望字节，同时保持解码后的值不变。
2. 按“成功插入才递增”的方式修改 ids，预测 next_id 与表中编号。
3. 在恢复目标 restored 已经存在时，再设计一次冲突处理，确保节点仍有明确去向。
4. 为普通帧增加校验字段，说明字节编码、校验失败与缓存插入应分别在哪里处理。
