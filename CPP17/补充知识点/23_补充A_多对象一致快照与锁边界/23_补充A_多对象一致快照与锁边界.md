# 补充 23A · 多对象一致快照与锁边界（C++17）

> 阅读顺序为第 23 课之后，不占每日主线编号。
> 所需标准为 C++17。配套代码见 [23a_consistent_snapshot.cpp](23a_consistent_snapshot.cpp)。

## 一、底层原理

### 1.1 每次读取有锁，为什么还可能读错组合？

假设两个计数器总是一起增加，业务要求任何一次观察都满足 left == right。
写者同时锁住两个对象并完成更新。

如果读者先锁 left、复制后解锁，再锁 right，就可能在两次读取之间遇到一次更新，
得到 `(5, 6)`。每个字段的访问都受到保护，仍然没有得到整个组合的一致快照。
需要读取组合状态时，读取区间也应同时持有相关对象的锁。

### 1.2 scoped_lock 如何决定共享还是独占？

直接传入 shared_mutex：

```cpp
std::scoped_lock lock(first.mutex, second.mutex);
```

调用的是它们的独占加锁接口，适合一起修改数据。
shared_mutex 这个类型的名字不会让 scoped_lock 自动选择共享模式。

读取时可以先建立两个尚未加锁的 shared_lock，再让 std::lock 协调它们：

```cpp
std::shared_lock left(first.mutex, std::defer_lock);
std::shared_lock right(second.mutex, std::defer_lock);
std::lock(left, right);
```

std::lock 操作的是包装器；shared_lock 的 lock() 再调用底层的 lock_shared()。
因此能同时持有两个共享锁，并在离开作用域时释放。

std::lock 属于之前标准已有的工具，本节将它与 C++17 的 shared_mutex、CTAD 组合。
多锁算法会规避这次组合加锁的死锁，具体尝试顺序和退避策略未指定；
它不能替整个程序消除锁外等待、递归加锁或其他不一致的加锁协议。

## 二、具体语法

### 2.1 同一对象作为两个参数传入时怎么办？

`snapshot(counter, counter)` 中两个参数指向同一个对象。
shared_mutex 不支持同一线程递归持有，连重复取得共享所有权也不允许。
因此应在组合加锁之前识别别名：

```cpp
if (&first == &second) {
    std::shared_lock lock(first.mutex);
    return {first.value, first.value};
}
```

写入接口也要提前分支。本例约定“每个不同对象增加一次”，
所以 `advance(counter, counter)` 只增加一次。
先定义业务含义，再选择锁法，不能依赖重复锁同一把锁的偶然表现。

### 2.2 const 接口为何配 mutable 锁？

snapshot 接收 const Counter&，它只观察业务数据。
锁本身为了同步仍需改变状态，所以 Counter::mutex 声明为 mutable。
这不会让 value 变成可随意修改的数据；写入仍需要独占锁并遵守统一协议。

### 2.3 返回值要在锁内复制

```cpp
return {first.value, second.value};
```

构造返回 pair 时两个锁仍持有，之后局部锁对象析构。
调用者取得独立副本，后续更新不会改变已经取得的快照。

如果返回内部引用、指针或引用成员的 pair，函数返回时锁已经释放，
使用者继续读这些引用就失去了这里的保护。
确需暴露引用时，需要另行设计持锁生命周期，不能直接套用当前接口。

## 三、实际应用与最佳实践

示例包含两个写者：分别按 (left, right) 和 (right, left) 顺序请求更新，
各执行 1000 次。另一个任务取得 1500 份一致快照，
逐次检查两个计数相等。最终两个值都应为 2000。

主线程通过 future::get() 等待任务，并接收任务内抛出的异常。
Counter 比 future 更早声明，异常退出时，使用 launch::async 创建的任务也会在
相关 future 的销毁过程中先完成，避免任务继续访问已经销毁的局部对象。

这适合关联配置、两个资源统计值或其他需要同时观察的少量对象。
如果业务本来就只需要整体更新与读取，把关联数据合并到一个对象并使用一把锁，
通常更容易维护；按对象分别加锁适合还需要独立访问的情况。

## 常见陷阱

- 以为“分别有锁”必然等于“组合一致”；应明确业务不变量跨越哪些字段。
- 已持有共享锁，再直接取得独占锁；shared_mutex 没有通用的原子升级接口。
  放掉读锁再取写锁时，中间状态可能变化，需要重新验证。
- 重复锁同一个 shared_mutex；在调用多锁算法前处理参数别名。
- 依赖“固定先锁第一个、逆序释放”的实现细节；scoped_lock 不提供这种顺序保证。
- 把读写锁当成性能保证；公平性和等待次序不能由这里推出，应按实际负载测量。

## 完整示例

在仓库根目录编译运行：

```powershell
g++ -std=c++17 -Wall -Wextra -Wpedantic -pthread "CPP17/补充知识点/23_补充A_多对象一致快照与锁边界/23a_consistent_snapshot.cpp" -o run.exe
.\run.exe
```

预期输出包括 `alias snapshot: 1 1`、`reader checks: PASS`、
`before: 0 0`、`after: 2000 2000`，最后为 `checks: PASS`。
验证依据是状态不变量与最终计数，运行时间不作为正确性门槛。
调度由系统决定，这次运行不保证每一种线程交错都出现；检查通过也不是并发正确性的完整证明。

## 练习

1. 解释返回 before 的那次快照为什么不随计数器增长。
2. 新增一个只读取单个 Counter 的接口，说明它能保证什么、不能保证什么。
3. 把两个 Counter 合并为一个 PairCounter，用一把 shared_mutex 重写，比较接口复杂度。
4. 若要实现“读后有条件更新”，说明释放共享锁并重新取得独占锁后需要重新检查什么。
