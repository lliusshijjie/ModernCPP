# 补充 28A · 求值定序与接口写法（C++17）

> 阅读顺序为第 28 课之后，不占每日主线编号。
> 所需标准为 C++17。配套代码见 [28a_sequencing_boundaries.cpp](28a_sequencing_boundaries.cpp)。

## 一、底层原理

### 1.1 同一个重载函数，调用写法不同也要重新分析

假设定义了非成员重载：

```cpp
Sink operator<<(Sink left, int right);
```

下面两种写法都能调用它，但操作数的定序规则不同：

| 写法 | C++17 的求值约定 |
|---|---|
| `make_sink(trace) << make_value(trace)` | 运算符写法，沿用内置 << 的定序：左操作数先于右操作数 |
| `operator<<(make_sink(trace), make_value(trace))` | 显式函数调用，两个形参的初始化不确定先后，但不交错 |

“重载运算符最终调用函数”可以帮助理解重载决议，
但不能由此把两种写法的求值顺序也当成完全相同。
把表达式改写成显式函数调用时，应重新检查副作用之间的依赖。

示例用 L、R、C 依次记录左操作数、右操作数和函数体。
运算符写法必须得到 LRC；显式函数调用允许 LRC 或 RLC。
程序接受这两种结果，不要求编译器改变其惯常选择，也不把某次结果当成唯一标准。

### 1.2 有定序不等于会短路

内置 && 和 || 会按条件决定是否求值右操作数。
重载版本使用运算符写法时有相应的操作数定序，但不会获得内置版本的短路能力：
为了调用重载函数，两个实参都需要准备好。

因此，有副作用的逻辑条件应先确认操作数类型。
“看起来还是 &&”不足以证明右侧一定不会执行。

## 二、具体语法

### 2.1 列表初始化与普通函数实参需要分开

```cpp
std::array<int, 3> values{
    mark(trace, 'A', 1),
    mark(trace, 'B', 2),
    mark(trace, 'C', 3)
};
```

花括号列表中的 initializer-clause 按出现顺序求值，示例得到 ABC。
这个规则在 C++11 已存在，不属于 C++17 才新增的保证。

不要把函数实参之间用于分隔的逗号理解为内置逗号运算符：

```cpp
consume(first(), second()); // 参数分隔符，不要求先 first。
(first(), second());       // 内置逗号表达式，先 first，再 second。
```

把列表中的值先准备好，再使用 apply 等工具调用，能够明确准备阶段的顺序。
但函数式构造、make_tuple 等普通调用的实参，仍按函数调用规则分析。

### 2.2 函数体执行顺序与实参对应位置也不同

即使实现先计算右边实参，右边表达式的结果仍传给第二个形参。
未指定先后不会让形参位置随机变化。
真正容易出错的是两个表达式依赖同一个会改变的状态。

例如 Reader::read() 每次读取当前字段并推进游标：

```cpp
// 不推荐：这两个 read() 的先后会影响它们读到哪个字段。
// submit(input.read(), input.read());

const int item = input.read();
const int count = input.read();
submit(item, count);
```

第二种写法直接把协议字段顺序写出来，参数表达式中不再推进游标。
这也是本节应用部分的处理方式。

### 2.3 不交错不能替代资源所有权

第 28 课的 unique_ptr 实参在自身求值过程中接管资源，
所以另一个实参抛异常时，已经构造的智能指针可以释放对象。

如果只把裸指针作为实参，则没有自动获得这个保护：

```cpp
// 仅分析，不运行：若先完成 new，另一个实参随后抛出，而接口尚未接管资源，可能泄漏。
// accept_raw(new Resource, may_throw());
```

C++17 约束求值的关系，不替接口设计资源释放责任。
先取得 RAII 对象，再传递其所有权，通常更清楚。

## 三、实际应用与最佳实践

示例的请求字段固定为 item=17、count=3。
读取游标的步骤分别完成，再构造只含普通整数值的 Request。
这适合顺序读取协议字段、执行有依赖的配置步骤，或调用会改变游标的解析接口。

评审这类代码可以依次问：

1. 当前使用的是运算符写法、普通函数调用，还是列表初始化？
2. 哪些子表达式会修改状态，后续步骤是否依赖这些修改？
3. 语言只保证不交错，还是已经保证具体先后？
4. 若有异常，资源由哪个已经完成构造的对象负责释放？

这些规则描述同一线程中表达式的求值关系，
不构成跨线程同步，不能据此省略锁或原子操作。

## 常见陷阱

- 将重载运算符改写成显式函数调用，却沿用原来的操作数顺序结论。
- 将参数分隔逗号与内置逗号运算符混为一谈。
- 看到重载 && 就依赖短路；定序与是否求值右侧是两件事。
- 对 read()、next_id++ 等状态推进操作，只证明没有 UB，却没检查业务结果是否确定。
- 用单次运行结果证明标准顺序；编译器、优化级别和具体表达式都可能影响允许范围内的选择。

## 完整示例

从仓库根目录执行：

```powershell
g++ -std=c++17 -Wall -Wextra -Wpedantic "CPP17/补充知识点/28_补充A_求值定序与接口写法/28a_sequencing_boundaries.cpp" -o run.exe
.\run.exe
```

预期输出 `operator notation: LRC`、
`function notation: LRC` 或 `function notation: RLC`、
`allowed order: true`、`braced list: ABC`、
`request: 17 3`，最后为 `checks: PASS`。
默认示例不执行无排序的重复修改。

## 练习

1. 为 Sink 增加成员函数 emit(int)，分析 make_sink(trace).emit(make_value(trace)) 的顺序。
2. 将请求准备阶段改为 `Request{input.read(), input.read()}`，判断字段顺序是否有保证。
3. 写两个分别返回 bool 与自定义类型的 && 示例，比较右侧是否执行。
4. 对比 make_tuple(first(), second()) 与 `std::tuple{first(), second()}` 的求值顺序；
   同时说明这里讨论顺序，并不声称两种构造的类型规则完全相同。
