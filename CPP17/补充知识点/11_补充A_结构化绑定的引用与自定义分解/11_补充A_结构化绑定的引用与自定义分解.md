# 补充 11A · 结构化绑定的引用与自定义分解（C++17）

> 阅读顺序：第 11 课之后；自定义 `get` 中的 `if constexpr` 可在第 13 课后回看。
> 所需标准：C++17 ｜ 独立代码：`11a_binding_protocol.cpp` ｜ 不占每日主线编号。

## 一、底层原理

### 1.1 复制隐藏对象，不等于复制所有被引用的对象

`auto [a, b] = obj` 先用 `obj` 初始化隐藏对象，再根据相应分解规则引入绑定。
如果隐藏对象的成员本来就是引用，复制这个对象后，引用仍然指向原来的目标：

```cpp
int value = 7;
std::tuple<int, int&> row{1, value};
auto [number, alias] = row;
number = 99; // 改的是隐藏 tuple 的第一个元素。
alias = 20;  // 引用元素仍指向 value，所以 value 变成 20。
```

因此“`auto` 一定与原对象完全隔离”并不成立。复制一个含指针、引用或视图的对象，
也不会自动取得其间接引用数据的所有权。

### 1.2 `decltype(name)` 有专门规则

对于 tuple-like 分解，未加括号的绑定名使用对应 `tuple_element<I, E>::type`，
而不是简单照搬 `decltype(get<I>(e))`。后者经常是引用，但元素声明类型可能是 `int`。

| 对上例的查询 | 结果 | 原因 |
|---|---|---|
| `decltype(number)` | `int` | tuple 的第一个元素类型 |
| `decltype(alias)` | `int&` | tuple 的第二个元素本来就是引用 |
| `decltype((number))` | `int&` | 加括号后按一般左值表达式规则处理 |

数据成员分解依据成员的声明类型及适用的 cv 限定；引用成员也不会凭空去掉引用。
普通可寻址元素的绑定名可以取地址，也可以用于 `sizeof`；位域不能取地址。

### 1.3 `const` 不会沿着引用传播

对 `tuple<int, int&>` 使用 `const auto& [a, b]` 时，`a` 是只读的，
`b` 仍然对应 `int&`。`const tuple` 不会把引用所指向的另一个对象变成 const。
判断是否可写时，需要同时查看绑定形式和元素类型。

## 二、具体语法

### 2.1 三种选择及生命周期

- `auto [a, b] = obj`：用值对象作为分解基础；是否共享间接数据取决于元素类型。
- `auto& [a, b] = obj`：绑定具名左值，修改可写元素会影响原对象。
- `const auto& [a, b] = make_obj()`：直接绑定临时对象时，可延长该临时对象的生命周期。

生命周期延长只作用于实际绑定的临时对象，不能修复其成员中已经悬空的指针或引用。
例如 `std::minmax(3, 7)` 返回的 pair 含有临时整数的引用，延长 pair 本身的生命也无济于事。

### 2.2 自定义 tuple-like 协议

配套代码让有 3 个成员的 `sensor::Reading` 只分解出 `channel`、`value`：

1. 为用户自定义类型特化 `std::tuple_size`，声明元素数量为 2。
2. 特化 `std::tuple_element<I, Reading>`，声明各元素类型。
3. 在 `sensor` 命名空间提供 `get<I>`，由 ADL 找到。
4. 按需提供左值、const 左值和右值版本，正确保留元素的值类别。

```cpp
sensor::Reading reading{2, 18.5, true};
auto& [channel, value] = reading;
value = 21.5; // 直接修改 reading.value。
```

结构化绑定会优先采用适用的 tuple-like 协议，不会因为协议实现错误就自动改走成员分解。
不要向 `std` 添加一个新的 `get` 重载；自定义类型的自由 `get` 应位于其关联命名空间。
编译器也可以使用合规的成员 `get`，本例选择 ADL 方案。

### 2.3 Lambda 的版本边界

C++17 可通过初始化捕获引入一个新变量：`[snapshot = alias] { return snapshot; }`。
按值捕获创建快照；`[&reference = alias]` 则要求被引用对象在调用时仍然存活。
C++20 才允许直接捕获结构化绑定名，不应把该能力写成 C++17 代码的前提。

## 三、实际应用与最佳实践

### 3.1 场景：为业务对象提供稳定的分解视图

传感器记录可以包含校验状态、时间戳等内部字段，而公开的二元分解只暴露通道与数值。
这种协议需要维护成本：元素数量、元素类型和所有 `get` 重载必须一致，
并且改变分解顺序会影响调用方。简单的数据成员结构通常直接分解即可。

### 3.2 最佳实践

先判断需要副本还是别名，再检查元素是否含引用；用 `static_assert` 核对关键返回类型。
通过 `const auto&` 阅读元素时，也要留意引用元素的可写性。
返回局部对象时返回值快照，避免把局部对象成员的引用暴露给调用者。

## 常见陷阱

1. 把 `decltype(binding)` 和 `decltype((binding))` 当成同一个查询。
2. 以为复制 tuple 就复制了其引用指向的数据。
3. 只实现 `get(Reading&)`，随后发现按值分解需要处理隐藏对象的右值访问。
4. 将 `std::get` 的新重载放进 `std`，或特化数量后遗漏元素类型。
5. 把引用延长 pair 生命周期误当成修复 `minmax` 临时实参的办法。
