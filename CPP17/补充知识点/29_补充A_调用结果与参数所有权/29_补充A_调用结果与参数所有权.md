# 补充 29A · 调用结果与参数所有权（C++17）

> 阅读顺序为第 29 课之后，不占每日主线编号。
> 所需标准为 C++17。配套代码见 [29a_invocation_ownership.cpp](29a_invocation_ownership.cpp)。

## 一、底层原理

### 1.1 统一语法之后，返回值仍有类型与值类别

invoke 解决“如何调用”。
它不会把所有调用都变成按值返回，也不会替使用者决定是否保存一个借用引用。

本例的 Meter 含有 int value：

| 对象实参 | `std::invoke(&Meter::value, 对象)` 的结果 |
|---|---|
| Meter& | int& |
| const Meter& | const int& |
| Meter&& | int&& |

通过 invoke_result_t 可以在编译期验证这些结果。
对临时对象取得成员引用，并不会替临时对象延长寿命；
配套程序只在仍然有效的拥有者上使用这些引用。

### 1.2 包装器保留引用，接收者仍可能复制

```cpp
auto snapshot = call(&Meter::value, meter);
decltype(auto) alias = call(&Meter::value, meter);
```

call 使用 decltype(auto) 返回 invoke 的原结果。
但 snapshot 声明使用 auto，得到独立的 int；
alias 使用 decltype(auto)，保留 int&。
因此 alias += 5 改变 meter.value，而 snapshot 仍是之前的 10。

这两个位置都要检查：包装器有没有保留结果类别，调用者又如何接收它。

## 二、具体语法

### 2.1 可调用性与异常属性可以由同一套调用规则判断

```cpp
template <class F, class... Args>
decltype(auto) call(F&& f, Args&&... args)
    noexcept(std::is_nothrow_invocable_v<F&&, Args&&...>) {
    return std::invoke(std::forward<F>(f), std::forward<Args>(args)...);
}
```

is_invocable_v 判断给定 callable 与实参组合是否可调用。
本例非 const 的 Meter::add 可以作用于 Meter&，不能作用于 const Meter&。
is_nothrow_invocable_v 则把实际调用的异常约定传递给包装器。

这里的 noexcept 只描述进入包装器之后对应调用的约定。
在调用包装器之前准备实参的构造、分配等步骤，需要另行分析。
trait 也不检查指针是否为空、引用是否悬空等运行期有效性。

### 2.2 tuple 是拥有副本，还是保存借用？

```cpp
auto owned = std::make_tuple(meter, 2);
auto borrowed = std::make_tuple(std::ref(meter), 3);
```

第一行复制 Meter，owned 中的元素拥有自己的状态。
第二行 make_tuple 特别识别 reference_wrapper，生成 tuple<Meter&, int>，
因此 apply 解包后操作的是原 meter。

| 打包方式 | 适用目的 | 生命周期责任 |
|---|---|---|
| make_tuple(lvalue) | 保存对象副本 | 副本自己拥有状态 |
| make_tuple(std::move(value)) | 尝试将对象移入 tuple | 原对象可能变为已移动状态 |
| make_tuple(std::ref(value)) / tie(value) | 保存左值借用 | 原对象必须覆盖后续使用 |
| forward_as_tuple(...) | 即时转发引用 | 不延长实参寿命，尤其不能长期保存临时对象的引用 |

借用 tuple 对象活着，不表示它引用的对象仍然活着。

### 2.3 apply 的传入类别会继续影响元素类别

示例把 unique_ptr 放进 arguments。
当 arguments 是左值 tuple 时，get 得到 unique_ptr&，
不能拷贝给一个按值接收 unique_ptr 的函数。

```cpp
const int result = std::apply(consume, std::move(arguments));
```

传入右值 tuple 后，元素能够以右值引用转发，按值形参取得其中的 unique_ptr。
本例执行后原 tuple 的指针变空。不能仅凭写了 std::move 就推断所有调用都会消耗元素：
是否真的移动，还取决于接收函数的参数和执行内容。

另外，C++17 的 apply 已经是 constexpr，示例使用 static_assert 验证普通函数的编译期调用。
std::invoke 自身到 C++20 才标为 constexpr；两者不能混为同一个引入时间。

### 2.4 可调用，不一定能装进 std::function

捕获 unique_ptr 的闭包可以正常保存和调用，但通常只能移动，不能拷贝。
C++17 的 std::function 要求被存储的目标可拷贝；
把该闭包再包一层 std::move 也不能取消这个要求。

示例直接保存具体闭包类型并调用。
需要统一保存 move-only 任务时，可按用途考虑 packaged_task 等 C++17 工具，
或另行设计任务容器；std::move_only_function 属于 C++23，不能提前当作本节可用接口。
用 std::ref 避开目标拷贝会转为借用，也必须维护原闭包的生命周期。

## 三、实际应用与最佳实践

本例依次处理成员访问、对象参数打包与资源消费。
它适合检查回调适配器、延迟任务、命令参数和泛型成员访问器：

1. 是否可调用，由 callable、对象的 const 属性及实参类别共同决定。
2. 结果需要快照还是借用，由返回类型与接收声明共同决定。
3. 延迟执行前必须决定参数是复制、移入还是引用。
4. 类型擦除工具的拷贝要求与调用协议要单独检查。

在增加线程之前，先把这些所有权选择明确下来，
能减少把已经悬空或被移走的对象带入异步执行的情况。

## 常见陷阱

- 包装器返回 auto，意外把成员引用变成副本。
- 使用 decltype(auto) 保留了引用，却忽略其拥有者的寿命。
- 认为 make_tuple 一律复制；右值可能移动，std::ref 还会被转换成引用元素。
- 对含 move-only 元素的左值 tuple 进行按值消费。
- 认为 invoke 支持任何 callable，就等于 std::function 能存储任意目标。

## 完整示例

从仓库根目录执行：

```powershell
g++ -std=c++17 -Wall -Wextra -Wpedantic "CPP17/补充知识点/29_补充A_调用结果与参数所有权/29a_invocation_ownership.cpp" -o run.exe
.\run.exe
```

预期输出 `snapshot/member: 10 15`、`copy/original: 17 18`、
`consumed: 42 source empty=true`、`move-only task: 7`，
最后为 `checks: PASS`。类型与 noexcept 的检查在编译期完成。

单独开启不符合 std::function 目标要求的调用，预期编译失败：

```powershell
g++ -std=c++17 -DLESSON29A_COPY_TARGET -Wall -Wextra -Wpedantic "CPP17/补充知识点/29_补充A_调用结果与参数所有权/29a_invocation_ownership.cpp" -o bad_target.exe
```

诊断应说明目标不满足可拷贝要求，具体措辞依编译器而异。

## 练习

1. 将 alias 的声明改成 auto，预测 meter.value 的变化并调整检查。
2. 把 borrowed 改成 make_tuple(meter, 3)，说明两个 add 分别更新谁。
3. 把 consume 改为接收 const unique_ptr<int>&，分析还需不需要移动 tuple，以及原指针是否变空。
4. 用 std::is_invocable_v 检查 Meter::add 与 const Meter*、std::reference_wrapper<Meter> 的组合。
