## 一、底层原理

### 1.1 一个任务，三副面孔

同一个"解析端口号"（第 51 课示例①），三种实现的**失败表达**决定
调用方的生活质量：

| 维度 | 异常 | 错误码 + out 参 | expected |
|---|---|---|---|
| 失败如何表达 | 控制流跳转（隐藏 return） | 返回值 | 返回值的一部分 |
| 忘处理后果 | 异常穿透（至少炸得出来） | **静默错**（最危险） | 类型逼你拆包 + nodiscard |
| 组合传播 | 自动穿透（免费但隐式） | 每层手搬（样板最重） | and_then 短路（显式且轻） |
| 错误信息量 | 任意异常类型 | 枚举（要另配表） | 任意 E |
| 开销模型 | 零成本模型 + 栈展开贵 | 最低 | 低（值返回） |
| 跨边界 | ABI 麻烦（-fno-exceptions） | C ABI 通货 | C++ 内部 |

**没有银弹**——三者是三种语义档位，不是三代进化。

### 1.2 语义判据：这算"流程"还是"事故"？

- **可预期、高频、属于业务流程**（用户输入错、查找未命中、
  校验不过）→ **expected**：调用方必须处理、处理路径要写出来
- **不可预期、违反不变量**（分配失败、深层违约、绝不该发生）→
  **异常**：让栈展开把烂摊子送到有能力兜底的一层
- **边界约束**（C ABI、热路径、嵌入式禁异常）→ **错误码**：
  最古老但最便宜，配 `ok` 显式枚举值 + out 参

### 1.3 传播形态对比（示例 ② 的三层实验）

"解析 → 加倍"两层组合，失败要穿透第一层：

- 异常版：**零行代码**穿透——代价是"会抛"成为隐式契约，
  读调用链看不见失败路径
- 错误码版：每层 if + return 搬运——错误可见但样板最重，
  且忘一层就静默漏
- expected 版：`and_then` 一层——错误路径**既显式又自动短路**，
  形态线性

### 1.4 混合策略：边界收拢

真实系统三件并用：**模块边界**用 `noexcept` 包装把内部异常
**翻译**成 expected（示例 ③ 的 safe_parse）；对外 C 接口再
翻译成错误码。错误**不越界**，每层用自己的母语。

## 二、具体语法（对照速查）

```cpp
// 异常
int parse_exc(std::string_view s);            // 失败 throw
try { parse_exc(s); } catch (const std::exception&) {}

// 错误码（注意：ok 必须是显式枚举值，别指望 ParseErr{} 恰好成功）
enum class ParseErr { ok, bad, out_of_range };
ParseErr parse_code(std::string_view s, int& out);

// expected
std::expected<int, ParseErr> parse_exp(std::string_view s);

// 边界翻译：异常世界 -> 值世界
auto safe = [](std::string_view s) noexcept -> std::expected<int, ParseErr> {
    try { return parse_exc(s); }
    catch (...) { return std::unexpected(ParseErr::bad); }
};
```

规则细则：

- 错误码风格**必须**有显式成功值（`ok`）——
  `return ParseErr{}` 是值初始化（= 第一个枚举），恰好当成功用
  纯属运气，是事故不是设计
- 异常翻译层标 `noexcept`（catch-all 收口）；expected 侧
  保持 `[[nodiscard]]`
- 一旦决定某模块 `-fno-exceptions`，expected/错误码是仅剩选项——
  但标准库仍可能抛（bad_alloc 等），边界要接得住
- 错误码的"原因文本"靠额外接口（error_table[e]）——expected
  可以直接携带，这是体验分水岭

## 三、实际应用与最佳实践

### 3.1 选型清单（示例 ③ 打印的结论）

| 场景 | 选择 |
|---|---|
| 解析 / 查找 / 校验 / 配置读取 | expected |
| 构造失败（工厂）/ 深层初始化 | 异常（构造函数没有返回值） |
| 跨 FFI / C ABI / 插件边界 | 错误码 |
| 嵌入式 / 实时 / 禁异常构建 | 错误码 或 expected |
| 迭代中的逐元素失败 | expected（继续处理其余） |
| 违约断言类 | 直接 terminate 比异常更诚实 |

### 3.2 最佳实践清单

1. **一个模块内只用一种**主要风格；边界做翻译（示例 ③）
2. expected 的 E 统一成项目错误 enum——顶层的 switch 分发
   就是错误清单文档
3. 异常路径**不参与**正常性能预算（零成本模型），但也别把
   热循环里的可预期失败塞进去（栈展开会真实计费）
4. 错误码风格靠 code review 与 `[[nodiscard]]` 枚举返回值双保险
5. 单元测试覆盖三种形态的成功/失败各一条路径（本课示例的形状）

## 常见陷阱

1. **错误码忘查**：`parse_code(s, port); 用 port`——bad 路径下
   port 是未初始化/旧值，静默错。本课示例 1.3 的 else 分支
   就是防它的最小形状
2. 把"可预期失败"写成异常：解析器每十个输入抛三次——
   栈展开成本进主路径，性能与可读性双输
3. 把"不变量破坏"写成 expected：每层都被迫搬运"绝不该发生"的
   错误，噪音淹没真流程
4. 异常穿越 noexcept 边界 → std::terminate——翻译层的 catch(...)
   收口是硬要求（示例 ③ 的形状）
5. expected 链末端忘 value_or/检查就 `*r`：同 optional 的 UB——
   链式写法让"末端"更醒目，别在中间拆包
6. 三种风格在同一函数里混用：调用方精神分裂——选定一种，
   翻译发生在边界而非函数体内

## 练习

1. 给示例的三种实现各加一个"域名解析"层（两跳失败传播），
   数一数每种风格新增的代码行数。
2. 用 `-fno-exceptions` 编译 expected 版与错误码版（异常版会
   编译失败或受限），体会禁异常世界的约束面。
3. 写异常→expected 的通用翻译模板：
   `template<class F> auto as_expected(F&& f) noexcept;`
   （提示：需要用 std::invoke_result_t 约定返回类型）。
4. 计时实验：解析失败率 50% 的输入集，异常版与 expected 版
   各跑一百万次，对比耗时并解释差距。
