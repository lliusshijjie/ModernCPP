# 第 51 课 · 综合：异常 / 错误码 / expected 的取舍（C++23）

> 所需标准：**C++23**（`-std=c++23`）｜ 独立代码：`51_error_handling.cpp`
> 本机示例使用 print，需链接 -lstdc++exp；这不是错误处理机制本身的要求。
> 前置：第 50 课（expected）；第 19 课（按语义选择类型）

## 一、底层原理

### 1.1 一个任务，三种失败接口

示例三种实现都按同一契约解析端口 **1..65535**：完整消费十进制字符串，
可有前导零，不接受符号、空白或尾随文本；失败时不修改错误码版本的 out。

| 维度 | 异常 | 状态码 + out | expected |
|---|---|---|---|
| 表达方式 | throw，沿调用栈传播 | 返回状态 | 返回值/错误的二选一结果 |
| 检查责任 | 在合适层捕获，未捕获可能终止 | 调用者检查状态 | 调用者检查、组合或显式忽略 |
| 传播 | 可不逐层写转发代码 | 通常逐层分支返回 | 可用 and_then 等组合 |
| 成本 | 依实现/ABI；抛出与展开通常较贵 | 依状态与接口设计 | 依 T/E、分支、构造和传递方式 |
| 跨边界 | 需兼容 ABI/运行库与异常约定 | 适合稳定的 C ABI | C++ 类型，通常在 C++ 边界内使用 |

expected 不强制拆包或处理，nodiscard 只是请求诊断。错误码也可使用
nodiscard，或返回含领域信息的结构；不能一概说原因只能另用输出参数。

### 1.2 先看恢复与接口约定，再选择语法

- 输入校验、未命中等常见失败若需要调用者分支，可用 expected。
- 异常适合把失败交给较远的恢复层，也可表达构造失败；可预期失败不一定
  禁止使用异常，低频解析失败或既有库接口仍可能合理采用它。
- C ABI、固定布局协议或受限运行环境常用状态码；禁异常的 C++ 内部代码
  也能用 expected，但仍须审核分配、库调用和失败策略。
- 不变量或前置条件违约按接口契约处理，可能是断言、终止或其他策略，
  不意味着一律抛异常，也不意味着 expected 会自动保证恢复安全。

### 1.3 成本模型不是性能排名

常说的“零成本异常”主要指某些 ABI 不在正常路径维护动态异常处理状态，
不表示二进制大小、优化限制、缓存及正常路径成本全部为零。错误码与 expected
也没有通用的固定快慢排名；按失败率、结果大小和实际工具链测量。

### 1.4 需要时在边界翻译

需要“不让异常越过此边界”时，可以捕获并转换成领域错误。noexcept 本身
不会执行转换：任何漏出的异常都会 terminate，包括处理错误时再次抛出的异常。
本课把 invalid_argument、out_of_range 和未知内部异常分开映射，避免把范围
错误、内存耗尽等一概伪装成普通输入错误。

## 二、具体语法

```cpp
enum class ParseErr { ok = 0, bad, out_of_range, internal };
[[nodiscard]] ParseErr parse_code(std::string_view, int& out);
[[nodiscard]] std::expected<int,ParseErr> parse_exp(std::string_view);
int parse_exc(std::string_view); // 失败时抛异常

auto safe_parse = [](std::string_view s) noexcept -> std::expected<int,ParseErr> {
    try { return parse_exc(s); }
    catch (const std::invalid_argument&) { return std::unexpected(ParseErr::bad); }
    catch (const std::out_of_range&) { return std::unexpected(ParseErr::out_of_range); }
    catch (...) { return std::unexpected(ParseErr::internal); }
};
```

规则细则：

- 枚举值初始化 `ParseErr{}` 得到**数值 0**，不保证是第一个枚举项；若首项为
  7，ParseErr{} 仍是 0，甚至可能不对应任何命名项。显式成功值与 `ParseErr::ok`
  的比较可清楚表达协议，而不是依赖枚举排列。
- catch-all 只在已决定转换所有异常、并能以不抛出的方式表示未知失败时使用。
  一般库代码不应随意吞掉异常；也可选择只捕获指定异常、保留异常中立性。
- `-fno-exceptions` 是编译器选项，不把异常自动变成错误码；GCC 下含 try/catch/
  throw 的源文件通常无法如此编译。expected 的 value()、分配和其他库调用也
  不因此天然安全；需要禁异常时必须单独审核可达调用路径与标准库配置。
- 构造函数不能直接返回 expected；可用返回 expected<对象,错误> 的工厂。
  因而“工厂构造失败只能用异常”也不成立。

## 三、实际应用与最佳实践

### 3.1 选择恢复位置与所有权

解析接口可返回 expected；多层初始化若采用异常，应依赖 RAII 保证失败后的
资源清理。C 接口边界可用不抛出的包装把失败映射为固定状态，不让 C 调用者
面对未约定的 C++ 异常或类型布局。

### 3.2 保持三种实现的契约一致

对比失败表达之前先统一合法输入、有效范围和错误优先级。本课用同样的
from_chars 检查完整消费，避免某一版接受 0、另一版接受 8080xyz 或漏出溢出。
错误码版先保存在局部变量，仅成功时写 out。

### 3.3 最佳实践清单

1. 按模块/接口约定统一主要风格，在有实际约束的边界翻译。
2. 给重要状态结果加 nodiscard，并测试调用者实际处理路径。
3. 说明哪些失败返回、哪些异常仍会传播；不要把 expected 当作 noexcept 标记。
4. 计时实验同时报告成功率、失败率、编译选项与结果类型大小。
5. 覆盖成功、无效字符、尾随文本、零值、上界及超长数字输入。

## 常见陷阱

1. 错误码忽略后使用旧 out；成功状态判断与输出读取必须绑定。
2. `noexcept` 包装只有声明而无合适处理，异常漏出仍会 terminate。
3. catch-all 把所有错误都变成 bad input，导致诊断与恢复策略失真。
4. expected 失败后直接 `*r` 是 UB；value() 会把失败转成访问异常，并非消除失败。
5. 为禁异常编译直接给含 throw/catch 的完整示例加 -fno-exceptions，不是有效实验。
6. 构造、IO、格式化和内存分配的异常契约须另外考虑。

## 完整示例

```bash
g++ -std=c++23 -Wall -Wextra "CPP23/51_错误处理三种方式取舍/51_error_handling.cpp" -o run -lstdc++exp && ./run
```

## 练习

1. 对三种端口解析接口运行同一组合法/非法输入，比较成功值与错误分类。
2. 另建只含 from_chars、状态码和 expected 的小程序，在 -fno-exceptions 下
   编译；不调用 value() 或带异常示例，并说明仍需审核哪些库操作。
3. 设计 as_expected 包装，区分 void 返回、引用返回以及错误构造可能抛出的情况，
   再决定能否声明 noexcept，不能无条件写死。
4. 对多个失败率分别测量异常版与 expected 版，并防止优化器消除计算。
